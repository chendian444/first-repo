# 完整压缩传输操作手册

本手册对应 reaction-wheel-compression-integration.zip 中的集成版本。操作以 Windows 为例。

软件协议、后端、页面及模拟串口链路已验证；AT32 真机的 Keil 完整编译、烧录和控制时序测试尚未完成。包中提供的是新的固件源码，没有可直接烧录的新 BIN。

## 一、先理解数据经过哪里

实时链路为：动量轮 16 通道 float32 → AT32 端 AUTO/ZRLE 或 RAW → USART3 DMA → USB-TTL → Python 采集 → HTTP 压缩帧 → Java 校验、解压 → 网页显示或 CSV 导出。

板端实施轻量无损压缩，Java/Vue 系统运行在电脑上。页面调整的是遥测压缩模式和遥测周期。解压由 Java 接收接口自动执行，无需手工点击“解压文件”。

## 二、准备电脑环境和目录

1. 解压 ZIP 到例如 `D:\WheelCompress`。找到包含 `firmware`、`DataCompress_System`、`serial-agent`、`examples` 的目录，以下称为“根目录”。例如完整路径为 `D:\WheelCompress\reaction-wheel-compression`。
2. 安装 Java 17、Node.js 18.17 或更新版本、Python 3.9 或更新版本，并让命令行可调用 java、node、python。
3. 在根目录打开 PowerShell，检查：

```powershell
java -version
node --version
python --version
```

后端 JAR、前端 dist、网关运行依赖已包含在包内。仅运行现有构建产物无需 Maven、无需重新构建前端。需要修改后端或前端时再按《集成说明》构建。

## 三、不接硬件，先验证上位机链路

在根目录的第一个 PowerShell 执行，并保持窗口运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\DataCompress_System\run.ps1
```

浏览器打开：

```text
http://localhost:8080/wheel
```

在根目录另开第二个 PowerShell：

```powershell
python .\serial-agent\wheel_agent.py --replay .\examples\historical-gyro.dcw --backend http://127.0.0.1:8082 --pace 0.2
```

预期：网页显示历史回放，有效帧累计增加、出现角速度曲线；终端最后显示历史回放完成 1000 帧。结束约 3 秒后回到等待设备，已接收数据仍可导出。

该例来自附件旧 CSV 的前 1000 行，中间预留通道为零，设备时间为测试重新生成。它验证接入、传输和解压，不代表实机轮速、电流或实机采样时序。重复回放会重新增加累计计数。

## 四、编译和烧录 AT32 固件

1. 安装 Keil µVision、原工程所用的 ARMCC 5.06，以及 ArteryTek.AT32F403A_407_DFP 设备包。
2. 打开 `firmware\USER\AT32F403A.uvprojx`，核对目标器件 AT32F403ARCT7。
3. 检查工程内有 WheelCodec.c、WheelTelemetry.c，新模块已加入工程；FOC 库保留为原来的 AT32F403A_FOC_LIB.lib。
4. 执行 Rebuild，确认无编译、链接错误，并检查 RAM/Flash 使用情况。
5. 按板卡实际调试器，在 Debug / Utilities 中选择相应下载器、SWD 和正确 Flash 算法，再 Download。调试器按原板卡方案连接 SWDIO、SWCLK、GND、目标电压参考；具体接口位置以原理图和实物为准。
6. 本工程默认生成 AXF，没有勾选 Create HEX File。可直接用 Keil 下载新编译的 AXF；需要 HEX 时在 Output 中勾选 Create HEX File 后重建；需要 BIN 时从新编译的 AXF 使用匹配的 ARM 工具转换，不使用原附件旧 BIN。
7. 下载完成后按原板卡方式复位。保留已有有效校准数据；原硬件如需校准，沿用原工程流程，避开持续遥测发送进行校准。

这一步仍需在实际 Keil/板卡上完成，当前包不包含已完成硬件验证的固件产物。

## 五、连接数据串口

使用 3.3 V 电平 USB-TTL：

| 动量轮 AT32 | USB-TTL |
|---|---|
| PB10 / USART3_TX | RX |
| PB11 / USART3_RX | TX |
| GND | GND |

板卡电源按原硬件配置供电。USB-TTL 的 VCC 不作为未经确认的动量轮供电连接。

串口配置为 230400 波特率、8 数据位、无校验、1 停止位。Windows 设备管理器中查看实际 COM 号，例如 COM4；关闭占用同一串口的其他程序。

## 六、开始实机压缩传输

确认第三节的上位机服务仍在运行。在根目录的采集终端执行：

```powershell
python -m pip install -r .\serial-agent\requirements.txt
python .\serial-agent\wheel_agent.py --port COM4 --enable-stream --backend http://127.0.0.1:8082
```

把 COM4 换成实际串口。

`--enable-stream` 在启动时发送原固件的开启打印命令 A0 AC 08 BA 66。新固件输出 DCW1 帧，旧 parse_debug.py 不再适用。

正常情况下：终端打印串口和记录文件路径，随后每 5 秒报告接收帧、上传帧、无效候选、待传批次；网页显示正在接收，最新数值、曲线和累计字节更新。

终端每次启动创建新的采集会话。板卡断电重启后如没有遥测，重新启动上述采集命令，以再次发送开启遥测指令。

## 七、从页面控制压缩并确认生效

在 `http://localhost:8080/wheel`：

1. 将压缩方式选择 AUTO，遥测周期设为 10 ms，点击应用配置。
2. 等待约 2 秒轮询及后续遥测返回，页面应显示设备已确认当前配置。
3. 检查实际模式/实际周期。AUTO 会在编码载荷不足 64 字节时使用 ZRLE，无压缩收益时使用 RAW；因此 AUTO 模式下实际编码偶尔为 RAW 属于正常行为。
4. 如需对比直传，将模式改为 RAW，周期仍设为 10 ms。确认生效后实际编码为 RAW。再切回 AUTO 比较同类工况下的字节统计。
5. 如需减少遥测流量，可设置 20 ms（50 Hz）、50 ms（20 Hz）或 100 ms（10 Hz）。允许范围为 10~1000 ms。该周期只改变遥测输出频率，不改变电机控制中断频率。

页面配置保存成功与设备配置生效是两个阶段。未连接采集程序或设备没有输出时，配置会保留在后端内存中，但不能视为已应用。服务重启后配置回到 AUTO、10 ms。

统计是后端启动以来的累计值，切换模式后不会清零。进行正式 AUTO/RAW 对比时，应使用相同数据和采样周期，并对比两个测试区间的新增字节、帧数；也可分别在干净重启的服务上测试。

## 八、确认完整性与查看结果

网页可查看角速度、姿态、轮速、FOC Iq、电压、保护状态和遥控通道。接收端自动执行 CRC16 校验，解压后每帧固定恢复 16 × 4 = 64 字节原始 float32。

| 指标 | 应如何理解 |
|---|---|
| 累计有效遥测帧 | 实际成功接收并解码的帧数 |
| 载荷节省 | 编码载荷与 64 字节原始载荷比较 |
| 同协议整帧节省 | 含头和 CRC 的帧与 86 字节 RAW 帧比较 |
| 序号缺口 | 也可能包含 DMA 忙跳过和采集调度延迟，不等同网络丢包率 |
| 拒绝批次 | 后端拒绝的请求数；串口坏帧在采集终端查看无效候选数 |

点击“导出最近 4000 帧 CSV”查看解压后的数值。服务端只保存当前采集会话最近 4000 帧；更换会话或判定设备重启时清空曲线缓存；服务关闭后内存数据丢失。

PC/模拟串口测试已验证无损往返。真实硬件验收还需核对测量量纲、实际帧与 CRC、压缩执行时间、控制周期及典型运行工况下的压缩率。

## 九、两台电脑之间传输压缩数据

例如电脑 A 接 USB-TTL，电脑 B 接收并显示，B 的局域网 IP 为 192.168.1.20。

1. B 电脑解压完整包，启动第三节的上位机服务。
2. A、B 网络互通，B 的 Java 后端 8082 端口可从 A 访问；远程看网页还需要 B 的 8080 端口可访问。必要时在 B 的防火墙中允许对应程序或端口。
3. A 电脑准备 serial-agent 文件夹并安装 requirements.txt。在包根目录执行：

```powershell
python .\serial-agent\wheel_agent.py --port COM4 --enable-stream --backend http://192.168.1.20:8082
```

4. B 电脑打开 `http://localhost:8080/wheel`，或 A 电脑打开 `http://192.168.1.20:8080/wheel`。
5. Java 接收的是压缩二进制帧，在 B 执行 CRC 校验和解压。页面配置也由 B 经 A 的采集程序下发至设备。

目前一个后端对应一个动量轮数据源，避免多个采集程序同时交错上传。

## 十、停止、保存和断网后恢复

在采集终端按 Ctrl+C 停止电脑采集。此操作不改变电机控制状态，也不发送关闭电机的指令；设备操作沿用原控制流程。板端仍可能继续输出遥测。

原始串口字节默认保存在执行采集命令时工作目录下的 `runtime\wheel-时间.dcw`。也可指定新路径：

```powershell
python .\serial-agent\wheel_agent.py --port COM4 --enable-stream --backend http://127.0.0.1:8082 --record .\runtime\test01.dcw
```

指定文件已存在时拒绝覆盖，每次采集使用新文件名。

断网时采集继续记录，网络线程重试。待传队列最多 100 批，队列满后将报告未上传丢弃帧数，但本地收到的原始字节仍在记录文件中。网络恢复后可先停止实时采集，再执行：

```powershell
python .\serial-agent\wheel_agent.py --replay .\runtime\test01.dcw --backend http://127.0.0.1:8082 --pace 0.2
```

回放会创建新会话并重新上传整份文件，不是按帧断点续传；此前已成功上传的数据可能再次计入累计统计。回放只能恢复电脑已收到并记录的帧，不能恢复串口上已丢失的数据。

## 十一、常见问题

| 现象 | 检查与处理 |
|---|---|
| 网页打不开 | 检查启动窗口；确认 Java/Node 命令存在，8080/8082 未被旧服务占用 |
| /api/wheel/status 返回 404 | 确认启动的是交付的新 JAR；原启动脚本可能复用已有的旧 8082 服务，先关闭旧实例再启动 |
| 串口打开失败 | 检查 COM 号、USB 驱动及是否被其他串口程序占用 |
| 有原始字节但没有有效帧 | 确认烧录了新固件、波特率正确，且使用 --enable-stream；旧 0x23 协议无法由新采集器解码 |
| 配置一直等待确认 | 检查采集程序指向的后端地址、串口 TX/RX、设备遥测输出；仅保存配置不会自动证明设备已应用 |
| AUTO 显示 RAW 或节省很低 | 当前数据压缩无收益时会自动直传；实际全部通道开启时的压缩率与含大量预留零的历史 CSV 不同 |
| 序号缺口增长 | 同时观察无效候选、队列丢弃、网络状态及主循环时序；可增大周期降低遥测负载 |
| 重启后没有原数据 | 后端是内存缓存；使用采集终端的 .dcw 原始记录回放 |

详细字段协议、源码改动、测试复现和验收边界另见《集成说明》《验证报告》。
