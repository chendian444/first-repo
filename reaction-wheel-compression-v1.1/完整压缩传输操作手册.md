# 动量轮完整26通道串口遥测 → 电脑压缩传输

更新：2026-11-09。本次只扩展串口遥测及电脑接收系统，继续使用现有无线控制，不需要手机App。

## 1. 必须先区分旧固件与完整遥测

你新上传的 `balanced-cube-v1.02(2).zip` 中，`UserFile/Debug.c` 的串口输出虽然有16个float通道，但4～14通道明确赋值为0，只有角速度XYZ、遥控X/Y有原始意义。电压、姿态角、编码器与Id/Iq在 `app.c` 中被用于LCD显示，并没有随这套旧串口协议发送。

因此，电脑软件不能从预留零还原出真实电流、轮速或电压。本次提供两种兼容接入：

| 模式 | 板端要求 | 实际数据 |
|---|---|---|
| legacy | 保留原旧固件 | 角速度XYZ、遥控X/Y；预留列仍保留并明确标识 |
| raw26 | 一次性更新“仅扩展遥测”的AT32程序 | 下表全部26通道，串口上不压缩 |

新字段要在实机出现，必须完成遥测固件的Rebuild、下载和Verify；仅替换电脑程序、打开网页或有现成无线控制都不会自动增加串口字段。新包不含已通过Keil/实机验收的BIN。

## 2. 完整26通道定义

| 序号 | CSV/API字段 | 固件变量 | 单位/说明 |
|---:|---|---|---|
| 1～3 | gyro_x/y/z | mpu6500.gyro.filter.x/y/z | °/s |
| 4～5 | angle_x/y | mpu6500.gyroAngle.x/y | °；原LCD的Cube_X/Y，不虚构未维护的姿态Z |
| 6～8 | wheel1/2/3_speed | M1/2/3_Encoder.Speed_filter | 原工程计算式对应°/s；RPM=数值/6，现场核对标定 |
| 9～11 | encoder1/2/3_raw | M1/2/3_Foc.Encoder_data | 编码器原始计数，不当作转速 |
| 12～14 | wheel1/2/3_id | M1/2/3_Foc.Id | FOC原始标定量，物理电流换算需核对 |
| 15～17 | wheel1/2/3_iq | M1/2/3_Foc.Iq | 同上 |
| 18 | battery_v | Cubli.BatVin | V，原LCD的Bat_DC |
| 19 | battery_filtered_v | Cubli.BatVin_filter | V，滤波值 |
| 20～22 | rc_x/y/z | Rc.x_f/y_f/z_f | 原遥控输入单位 |
| 23 | protect_flag | Cubli.Protect_flag | 状态值 |
| 24 | auto_mode | Cubli.AutoStandUp | 原自动模式值 |
| 25 | manual_mode | Cubli.ManualUp | 原手动模式值 |
| 26 | calibrated | Cubli.Cali_flag | 原校准状态值 |

每帧固定26个float32，共104字节。状态/编码器整数转换为float发送；浮点采样的原始位模式在电脑编解码过程中保留。读取不关闭控制中断，不能保证26个变量来自完全同一硬件采样瞬间。

## 3. 整体连接

```text
现有无线控制 → 原有控制链路（不改）
                         ↓
动量轮传感器 / 编码器 / FOC变量
  → AT32只采集、分帧、CRC校验码；不执行压缩
  → USART3原始RWT1帧，230400 / 8N1
  → USB-TTL → 电脑Python校验、ZRLE无损压缩或RAW回退
  → HTTP二进制帧 → Java校验、解压 → 网页全部通道/分组曲线/CSV
```

保持已验证接线：USB-TTL GND→AT32 Debug GND、RXD→板端TXD、TXD→板端RXD，使用兼容3.3V的信号电平，板卡独立供电。采集时板端DIO、CLK和电源脚不接USB-TTL。

COM号以当前设备管理器为准，下面以COM6为例。无线控制模块仍按原方式运行，不能把上传工程附带的ESP32 BLE源码当作你现有Wi-Fi模块的更新包烧录。

## 4. 下载新包并先验证电脑系统

下载[完整26通道运行包 v1.3](../deliverables/reaction-wheel-telemetry26-pc-v1.3.zip)，解压到新目录，保留旧目录与采集记录。进入同时含 `DataCompress_System`、`serial-agent`、`start-raw26.ps1`、`firmware-raw26` 的根目录。

需要Java17、Node.js18.17+及Python3.9+。包中包含新JAR、前端dist及网关依赖；旧v1.2的JAR不能解码本次26通道帧。

先停止旧采集与旧上位机实例，关闭XCOM串口。窗口A执行并保持运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\DataCompress_System\run.ps1
```

浏览器打开 `http://localhost:8080/wheel`。

窗口B先回放合成的26通道示例：

```powershell
python .\serial-agent\wheel_agent.py --protocol raw26 --replay .\examples\full-telemetry26.rwt --backend http://127.0.0.1:8082 --pace 0.2
```

预期1000帧完成，页面来源显示26通道、电脑压缩；选择不同“遥测分组”可看姿态、轮速、编码器、Id、Iq、电压、遥控和状态。该文件全部是合成演示，不是你的实机测量。切换为实时采集前结束回放。

## 5. 准备仅扩展遥测的AT32工程

运行包中的 `firmware-raw26` 已基于此次上传的原始工程生成，保留原许可证和FOC库，清理了旧BIN/AXF等构建产物。它与附件相比只修改以下五个文件：

1. `UserFile/Debug.c`：改为采集26通道，按100Hz输出原始RWT1帧。
2. `UserFile/Debug.h`：增加毫秒计数声明，保留原兼容符号。
3. `UserFile/timer.c`：原TMR7的1ms中断中增加一个毫秒计数递增。
4. `UserFile/usart.c`：USART3 DMA增加长度/忙检查，防止覆盖正在发送的缓冲；忙标志由发送函数管理。
5. `UserFile/usart.h`：USART3忙标志声明为volatile。

原应用调用顺序、电机控制、PID/FOC、遥控协议及ESP32文件保持原样。准备工具已逐文件核对，只改上述五个文件；不代表真实设备的控制时序已验收。

**如果你现用的无线控制工程与附件不同，应从你现用的工程生成新副本，不要整包替换现有控制源码。** 在本包根目录执行：

```powershell
python .\tools\prepare_raw26_firmware.py --source 'D:\你的现用工程' --output 'D:\Wheel-Raw26-New'
```

输出必须是不存在的新目录。工具先检查预期结构，匹配失败就拒绝；不覆盖原工程，不修改原目录。若现用工程结构不同，需要人工合并五处遥测改动。

## 6. 本地编译、下载及首次验收

1. Keil打开 `firmware-raw26\USER\AT32F403A.uvprojx`（或工具生成的新目录）。本包原来的 `firmware` 是旧板端压缩参考工程，不是这次raw26目标。
2. 核对真实器件AT32F403ARCT7、原ARMCC5及设备包/FOC库。完整Rebuild，确认0 Error(s)，核查警告、RAM/Flash和链接结果。
3. 下载前保留原固件及校准信息，核对工具擦除范围；不要为连接随意全片擦除或解除保护。
4. 用兼容的SWD下载器或经确认可用的ISP方式下载新AXF，Verify成功后复位运行。现有USB-TTL接USART3可以收发，但不能直接当作SWD；原厂ISP不支持这组USART3。
5. 首次在按原板流程固定、可控的条件下验证，再检查无线控制和电机控制时序。不要把云端语法/桩测试当成实机验收。

原 `A0 AC 08 BA 66` 开启遥测命令保留。板端默认100Hz（10ms）；122字节×100帧/秒，8N1约122000 bit/s，占230400约53%。这是带宽预算，不是CPU、控制抖动或端到端延迟的实测结果。

## 7. 实时采集并压缩上传

确认板卡已运行新raw26固件、XCOM已关闭、窗口A服务仍运行。在窗口B执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\start-raw26.ps1 -Port COM6
```

等效命令：

```powershell
python -m pip install -r .\serial-agent\requirements.txt
python .\serial-agent\wheel_agent.py --protocol raw26 --port COM6 --baud 230400 --enable-stream --backend http://127.0.0.1:8082
```

检查终端有效接收、上传计数持续增加；页面为“串口采集”，26个通道有对应数值，设备时间更新。Id/Iq或轮速在静止时可能接近0，不能只凭非零判断成功，需结合实际状态与标定。

若仍使用未更新的旧固件，使用下面命令接入已有数据，而不是raw26：

```powershell
powershell -ExecutionPolicy Bypass -File .\start-legacy.ps1 -Port COM6
```

旧模式依然只有原有角速度/遥控有效值，不能提供新增测量。详情见[旧固件电脑压缩手册](旧固件电脑压缩操作手册.md)。

## 8. 网页、周期与完整导出

- “遥测分组”可选择9类曲线；“最新通道数据”展示来源的所有字段。
- CSV导出与当前曲线选哪组无关，raw26每行含6列元数据和26列数据，共32列。
- CSV字段开头为 `sequence,device_ms,received_at,codec,mode,batch_period_ms`。设备序号/时间来自AT32；received_at是后端接收时间。
- AUTO/RAW配置在电脑执行，周期是电脑组批上传周期；最多20帧一批，满批可提前上传，不改变板端10ms遥测节奏，也不控制电机。
- 原始记录默认 `runtime\wheel-UTC时间.rwt`。可用 `--record .\runtime\test01.rwt` 指定，不覆盖已有文件。
- 后端仅缓存当前会话最近4000帧，100Hz约40秒，不是全程存档。重要CSV应在会话切换或服务停止前导出，全程原始串口数据使用.rwt记录。

保存和网络恢复后回放：

```powershell
python .\serial-agent\wheel_agent.py --protocol raw26 --replay .\runtime\test01.rwt --backend http://127.0.0.1:8082 --pace 0.2
```

回放保留原设备序号和设备时间，整文件重传创建新会话，可能重复累计已上传数据，不是断点续传。网络队列满会丢弃待上传帧，本地已经收到并记录的字节仍可回放；不能恢复串口未收到的内容。

## 9. 协议与统计口径

RWT1串口帧固定122字节，小于原DMA缓冲128字节：

| 偏移 | 长度 | 内容 |
|---:|---:|---|
| 0 | 4 | ASCII RWT1 |
| 4 | 1 | 布局版本1 |
| 5 | 1 | 通道数26 |
| 6 | 2 | 原始载荷长度104，小端 |
| 8 | 4 | 设备遥测槽序号，小端uint32 |
| 12 | 4 | 设备经过毫秒，小端uint32 |
| 16 | 104 | 26个小端float32 |
| 120 | 2 | 前120字节CRC-16/CCITT-FALSE，小端 |

电脑将104字节载荷无损编码后上传DCW1扩展帧：通道数26、来源标记2、最大126字节。Java只接受定义的来源/通道数组合，先整批CRC校验再入库；不把任意通道数解释成有效样本。

“载荷节省”比较104字节原始载荷；“同协议整帧节省”比较126字节RAW传输帧；“网络帧体相对输入帧节省”比较122字节原始串口帧。均不含HTTP/TCP开销，不是串口带宽节省。RAW封装会比122字节输入稍大，允许节省为负。

DMA忙或主循环延迟会跳过遥测槽，序号保留缺口；CRC错误、串口错误、网络队列丢弃也可能造成缺口，不能直接等同网络丢包率。

## 10. 排错与验收

| 现象 | 检查 |
|---|---|
| raw26采集有字节但无有效帧 | 确认板端已下载raw26新程序；旧0x23固件请用legacy模式；检查230400与CRC |
| 页面仍只有预留通道 | 检查来源是否LEGACY_0X23；仅换电脑软件不会改变板端字段 |
| 后端400拒绝26通道 | 确认启动本次新JAR，不是旧后台实例 |
| 曲线看不到Id/Iq/电压 | 切换遥测分组；核对最新通道表和CSV；不把0值当作不存在 |
| 接收增加上传不增加 | 检查8082/HTTP错误，保留.rwt；网页8080不等于上传端口 |
| 序号缺口增长 | 检查DMA、主循环、线长接地供电、CRC、队列；现场测量控制时序 |
| 下载后校准状态变化 | 核查原校准Flash区、擦除范围与恢复流程 |
| 停止采集后设备仍运行 | Ctrl+C只是停采，按原无线/物理流程停机 |

本次软件验证见[26通道验证报告](26通道验证报告.md)。完整Keil链接、烧录、Windows/COM6实机、量纲/校准及运行负载仍需现场验收。
