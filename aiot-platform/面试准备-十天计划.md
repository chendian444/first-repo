# AIOT测试工程师实习：十天准备

针对截图 J18413：AI工具提效、手机短距离通信和AIOT体验质量、测试脚本、体验模型；要求Android/嵌入式/数据库、Python或Java。目的不是十天造全栈物联网产品，而是能展示一条真实链路、完整测试设计和有证据的定位过程。

## 岗位与项目对应

| 岗位点 | 本项目可以证明 | 还必须补的知识/练习 |
|---|---|---|
| 设备与嵌入式 | AT32 UART、帧结构、CRC、采样/传输分离 | 中断/DMA、TTL电平、波特率、烧录与编译区别 |
| 自动化能力 | Python参数化场景、HTTP断言、SQLite证据、回归测试 | pytest fixture/parametrize、mock边界、CI测试分层（当前实现用unittest） |
| 短距离通信 | 设备→USB串口→网络网关的方法和定位 | BLE广播/扫描/连接/GATT/通知/MTU、经典蓝牙差别；Wi-Fi关联/DHCP/DNS/TCP |
| Android | 本项目不开发APP | adb、logcat、dumpsys、Android蓝牙权限和生命周期；有真机才做实操 |
| AI测试提效 | 在线统计异常基线和确定性报告分析 | 数据标注、误报漏报、精确率/召回率；LLM辅助生成用例需人工审查 |
| 用户体验模型 | 时延、成功率、恢复、一致性、新鲜度 | 首次连接、自动重连、多设备、距离/遮挡/干扰、功耗与场景权重 |

## Android实操清单

只在自己的测试手机上操作，先取得ADB授权；不需要做新APP。

```text
adb devices -l
adb shell getprop ro.build.version.release
adb shell dumpsys bluetooth_manager
adb shell dumpsys wifi
adb logcat -v threadtime
```

保存日志前去除账号、设备地址等个人信息。不要依赖固定log tag，因系统/OEM不同；记录操作时间并关联扫描、连接、断连事件。Android12+了解BLUETOOTH_SCAN/CONNECT运行时权限；较旧版本扫描可能涉及位置权限/位置开关，具体与targetSdk和系统有关。了解前后台、熄屏、省电策略对扫描/重连的影响。不能用ADB日志证明自己做过BLE应用开发。

测试场景：首次配对/首次连接、取消授权、蓝牙关闭再开、设备断电恢复、超距后回归、两手机争连、多设备列表、Wi-Fi与2.4GHz蓝牙共存、后台/熄屏。每个场景记录手机型号/系统、设备固件、距离遮挡、操作步骤、预期时间窗、重复次数和失败证据。射频和功耗结果需真实仪器/实测，不从本平台报告推导。

## 体验模型（待实测的验收目标，不是已达到的性能）

- 连接成功率=规定时间内完成连接次数/有效尝试次数；失败分类，不随意排除失败样本。
- 自动恢复成功率=无需人工干预恢复次数/故障解除次数；恢复耗时从“故障解除”到“首个有效新遥测”。
- 数据新鲜度=平台当前时间减网关采集时间，需说明两机时钟同步误差；旧协议不等于板端采样延迟。
- 数据一致性=解码后原始字节逐帧一致比例；用例另检验重复、缺失、顺序和会话边界。
- 时延报告分P50/P95/最大值、样本量与工况，不用5批数据声称正式SLA。
- 用户体验评分可先定权重：连接30%、恢复30%、数据质量25%、操作易用15%；权重是示例，需按业务和用户调研确认。

## 两分钟项目讲述模板

“我用动量轮作为设备端，保留原控制固件，通过USB-TTL采集遥测，电脑网关负责校验、无损压缩和上传。我发现原系统主要面向曲线显示，缺少设备身份、持久化待传队列和可重复的故障验证，于是补充设备令牌、SQLite outbox与按会话批次去重。

重点验证了服务端提交成功但ACK丢失这个场景：客户端重试同一批次，服务端应返回重复确认而不重复写样本。自动化还覆盖延迟、抖动、请求丢失、短时断开和限带宽。报告记录参数、种子、尝试次数、恢复后的数据一致性，并对解码后的原始字节作比较。

异常分析先用在线统计基线，明确预热和误报边界。现在完成的是软件链路和模拟串口验证；真实设备接入/无线/Windows验收以我的实测记录为准，不能把回放当实机结果。下一步补真实BLE/Wi-Fi场景和更长时间的稳定性测试。”

上段“我”仅在你已经读懂、运行并能解释代码后用于面试。尚未实机验收就保持最后一段，不改写为“实机全通过”。

## 高频追问及回答要点

1. 为什么电脑压缩？板端控制实时性优先，PC资源更足；无法减少原串口带宽，JSON/Base64开销也可能抵消收益。
2. 为什么不是MQTT？本版聚焦HTTP恢复验证、实现成本低；MQTT有会话/QoS等机制，但QoS不自动保证业务幂等或串口不丢数据。
3. HTTP超时是否等于失败？不一定，可能服务已提交但应答丢失；需要稳定幂等键和持久化ACK删除。
4. exactly-once做到了吗？仅同设备/会话/批次去重；新batch重放、串口尾批未落盘仍可能重复或缺失。
5. CRC与sum8区别？CRC检错更强但不是安全认证；电脑新增CRC不能修复此前未检出的串口损坏。
6. 如何定位无数据？供电→端口独占/电平/接线→波特率→字节计数→帧校验→本地待传→HTTP身份/服务→数据库→页面。
7. 设备在线却无数据？心跳只证明网关可达，要看串口状态、有效帧计数与最后采集时间。
8. 如何测重连？明确触发/解除时间、恢复定义、重试次数、无需人工操作、首个新帧、重复次数；当前小样本不是正式产品指标。
9. AI有什么价值？无监督基线提示偏离与非法值，减少人工筛查；不能替代物理量标定，启停工况可能误报。
10. 13V与显示4.4V怎么定位？先确认电池类型和安全，区分静态/带载电压，再查板端采样/分压/标定/显示；不能凭单点电压认定固件故障。
11. C9511E与C9555E？前者产品识别失败，后者授权检查失败；不属于C语法错误，不能通过修改遥测源码修复。
12. 面对海外场景如何建模？先按用户路径、网络/系统/设备环境、语言与操作习惯分层，用实际需求确定权重和验收门槛，避免对地域做未经验证的推断。
